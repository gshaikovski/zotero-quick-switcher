## 1. [HIGH] Items whose only attachment is a non-reader file (.docx, .pptx, image, .csv) never open — Enter silently reveals them in the library instead
**opener.js:104**

`_resolveAttachment()` only ever returns an attachment with a truthy `attachmentReaderType` ('pdf' | 'epub' | 'snapshot'); for every other content type it returns null (engine.js `_pickReaderAttachment` skips `if (!type) continue`). The fallback gate at opener.js:104 is `if (attachment || this._hasLaunchableURL(item))`, so an item whose only child attachment is a Word/PowerPoint/image/CSV/ZIP file — and which has no `url` and no DOI — fails BOTH halves of the gate and falls through to `revealInLibrary()`. But `ZoteroPane.viewItems()` would have handled it perfectly: `item.getBestAttachment()` excludes only LINK_MODE_LINKED_URL and deleted rows, not non-reader content types, so double-clicking the same row launches the file in the external app. The gate is narrower than the function it guards, and the code comment directly above it ("Mirror double-click: external app for a .docx") describes behaviour the gate makes unreachable.

- Failure: User has a journal article / manuscript whose only attachment is `draft.docx` (no URL, no DOI) — common for preprints, theses and grant material. They press Cmd+O, type the title, and press Enter. The overlay closes, the library tab is selected and the row is highlighted, and nothing else happens — Word never opens. Double-clicking the identical row in the items tree opens Word. Same for an item whose only attachment is a figure (.png) or a dataset (.csv).

Ground truth: /Users/george/.claude/jobs/be8c93f2/tmp/omni/chrome/content/zotero/xpcom/data/item.js:4040-4059 `getBestAttachments()` SQL filters only `linkMode NOT IN (LINKED_URL)` and `NOT IN deletedItems` — no content-type filter; item.js:3264-3280 `attachmentReaderType` returns undefined for anything that is not application/pdf, application/epub+zip or text/html; /Users/george/.claude/jobs/be8c93f2/tmp/omni/chrome/content/zotero/zoteroPane.js:5036-5041 viewItems → getBestAttachment → viewAttachment → Zotero.FileHandlers.open → fileHandlers.js:44-47 `Zotero.launchFile(path)`.
- Suggested fix: Do not use the reader-openable attachment as the gate for the viewItems fallback. Track whether the item has ANY non-linked-URL child attachment (e.g. `item.numAttachments()` / a second pass in `_pickReaderAttachment` that records a `hasAnyFileAttachment` flag on the index entry) and include that in the condition, or simply always call `viewItems([item])` and only fall back to `revealInLibrary` when the item has no attachments at all and no url/DOI.

## 2. [HIGH] tokenize() never strips interior/trailing punctuation, and the AND-across-tokens rejection then scores the exact paper the user typed at 0
**engine.js:328**

Every other punctuation character a user types — `,` `.` `?` `!` `(` `)` `-` — stays glued to the token. None of the seven haystacks in `entry.l` is punctuation-normalised either, so a token like `learning.` or `lecun,` fails `===`, `startsWith`, `indexOf`, and then fails `_subsequenceScore` too (the trailing `.`/`,` is simply not present in the field). `scoreEntry` line 397 (`if (best <= 0) return 0`) turns that single dead token into a hard rejection of the whole item. The consequence is not just "fewer results" — a *different, unrelated* item that happens to contain the punctuation elsewhere survives, lands at rank 1, is preselected, and Enter opens it.

## 3. [HIGH] _dirty set by the Notifier during an in-flight rebuild is clobbered by the unconditional `_dirty = false` at the end of the build
**engine.js:125**

`ensureIndex()` never snapshots `_dirty` at build start. The IIFE runs `this._entries = entries; this._dirty = false;` (lines 124-125) unconditionally when it finishes. The Notifier observer (line 61) can set `_dirty = true` at any of the four `await` points inside the loop (waitForDataLoad, Items.getAll, Items.getAsync, loadDataTypes) — that flag is then overwritten with `false`, and the item change it represented is lost. Nothing re-checks: the next `ensureIndex()` takes the fast path at line 87 and returns the stale array. The index only recovers when some *unrelated* later item event happens to set `_dirty` again.

- Failure: overlay.init() warms the index in the background at window-attach time (overlay.js:81), and Zotero's auto-sync runs at roughly the same moment. Every item the sync adds/modifies during that ~1s build fires 'add'/'modify' → `_dirty = true` → immediately clobbered to `false` when the build lands. The user opens Cmd+O and those papers are simply not findable, indefinitely. Same for: user edits a title in the item pane while the first search of the session is still building — the edit never reaches the index, and re-typing the query does not help because the fast path short-circuits.
- Evidence: Executed reproduction, /Users/george/.claude/jobs/be8c93f2/tmp/eng2.js T6 (run against the current engine.js snapshot):
  after build: _dirty = false  entries = 1  (getAll called 1x)
  search("second") -> 0 hits *** NEW ITEM INVISIBLE ***
  getAll calls after the search: 1 (no rebuild was triggered)
  search("second") again -> 0 hits, getAll calls: 1
The harness sets `_dirty = true` 5ms into a 30ms build (exactly what the Notifier observer at engine.js:55-63 does) and pushes a new item; the item is permanently absent and no rebuild is ever attempted.
- Suggested fix: Capture the generation at build start and only clear the flag if nothing changed meanwhile, e.g. `const gen = ++this._gen;` in the observer and `if (gen === this._gen) this._dirty = false;` after the loop — or simply set `this._dirty = false` *before* the loop starts so a mid-build notification survives.

## 4. [HIGH] open() nulls _lastPointer, so the first synthesized mousemove after the first render steals the selection — Enter opens the wrong paper
**overlay.js:401**

`open()` resets `this._lastPointer = null` (overlay.js:401). The mousemove guard at overlay.js:355-357 only suppresses Gecko's synthesized mousemove when `_lastPointer` already holds the current cursor position, so the *first* synthesized mousemove of every switcher session is unguarded. Gecko dispatches a synthetic `mousemove` at the last cursor position after every reflow (this is how :hover stays correct — the code's own comment at overlay.js:350-354 states the premise), and `_render()` calls `this._list.replaceChildren(frag)` (overlay.js:594), which is a reflow. So if the pointer happens to be resting anywhere over the region where the result list paints, the row under it silently becomes `_selectedIndex` before the user has touched the mouse. The modal is horizontally centred, 640px wide, starting at `padding-top: 12vh` (skin/quickSwitcher.css:29, 47) with a 520px list — i.e. the dead centre of the window, the single most likely place for an idle pointer. This breaks requirement 2 ("keeping the first entry selected") and consequently requirement 4 ("Enter opens the SELECTED paper").

- Failure: Pointer resting in the middle of the Zotero window (it does not need to move). Press Cmd+O, type `attention` quickly (all keystrokes inside the 110 ms debounce, so exactly one search and one render), press Enter. The row that happened to sit under the stationary cursor is opened instead of the top-ranked result. Executed repro: results [a1,a2,a3,a4], cursor over row index 1 → `_selectedIndex` becomes 1 and `ZQS_Opener.openEntry` receives `a2`, not `a1`. Note the bug only sticks when the last render is also the first render of the session, which is exactly the burst-type-then-Enter flow a quick switcher is built for; slow typing (a search per character) self-corrects because render #2 onward is guarded.

## 5. [HIGH] normalize() applies NFC (composing) instead of NFD + combining-mark stripping, so accented names/titles cannot be found by typing the unaccented form
**engine.js:302**

`normalize()` (engine.js:302-312) lowercases, folds curly quotes and then calls `out.normalize('NFC')` — NFC *composes* base+mark into a single precomposed codepoint, which is the opposite of what diacritic-insensitive matching needs. SPEC §4.4 specifies `.normalize('NFD').replace(/[̀-ͯ]/g,'')` so that "Müller" indexes as "muller". Because `scoreEntry` rejects an entry as soon as any token scores 0 (engine.js:397), a query token containing an ASCII letter where the index holds an accented one matches nothing in the creator/title fields and the correct paper is dropped entirely; the 50 rows the user does see are junk subsequence matches from `_subsequenceScore` (engine.js:356-375) on unrelated titles. This breaks requirement 2's "matching papers are listed in descending order of relevance" for any library with non-ASCII author names — i.e. essentially every academic library.

- Failure: User wants "Segment Anything" (Piotr Dollár) or "Masked Autoencoders Are Scalable Vision Learners". They press Cmd+O and type `dollar` — there is no way to type `á` on a US keyboard without a dead-key dance. Instead of those two papers, the switcher lists 204 results whose top 10 are "The Llama 3 Herd of Models", "Reinforcement World Model Learning for LLM-based Agents", "Loss of plasticity in deep continual learning", … and the first genuine Dollár paper is at rank 21, off-screen and unreachable within the 10 visible rows without arrowing 20 times.

## 6. [HIGH] Escape (and every other close path) leaves the chrome window with nothing focused, because the overlay blurs its input and simultaneously suppresses Zotero's own Escape→refocus-reader handler
**overlay.js:418**

So the plugin removes Zotero's focus-restoration and does not substitute its own. The same dead-focus state is produced by the backdrop mousedown handler (overlay.js:330-333), by the `deactivate` handler (overlay.js:77), and by Cmd+Enter (background:true), where opener.js:90 calls Zotero.Reader.open({openInBackground:true}) so Zotero_Tabs.select() — and therefore its setTimeout(...,0) refocus hook — never runs.

- Failure: User is reading a PDF in a reader tab, presses Cmd+O, changes their mind and presses Escape. The overlay hides, but nothing in the window has keyboard focus any more: Page Down / arrow keys no longer scroll the PDF, the reader's own shortcuts are dead, and typing does nothing. The user has to click into the PDF to get back to where they were. Without the plugin, that same Escape would have called Zotero.Reader.getByTabID(...).focus().

## 7. [HIGH] The overlay is not a focus trap: Tab (and Zotero's global tab shortcuts) move focus out from under a still-visible overlay that keeps swallowing Enter/Arrows/Escape

## 8. [MEDIUM] Notifier observer leaks for the rest of the session when the main window is already dead at onMainWindowUnload
**bootstrap.js:88**

The only handle bootstrap keeps on anything it registered is `win.ZQS_Overlay`; the process-global `Zotero.Notifier` observer registered by `ZQS_Engine.init()` is reachable only by reading that window property and then running `ZQS_Overlay.destroy()` to completion. `destroy()` unregisters the observer LAST (src/overlay.js:117, via `win.ZQS_Engine.destroy()`), after two UNGUARDED `win.removeEventListener(...)` calls (src/overlay.js:102-107). Zotero does not deliver `onMainWindowUnload` synchronously — `plugins.js` `onCloseWindow` awaits `AddonManager.getActiveAddons()` before calling the hook — so the hook can land after the window's wrappers are nuked. From then on every item add/modify/delete/trash re-enters the dead window's arrow function; `Zotero.Notifier.trigger` catches the resulting "can't access dead object" and calls `Zotero.logError` for it — one Error Console entry per notification for the rest of the session — and the closed ChromeWindow can never be garbage collected because `_observers` pins it.

## 9. [MEDIUM] shutdown() cannot cancel an in-flight attach, and startup() discards the attachedWindows record — a disable/enable across that window leaves two overlays and a permanently dead hotkey
**bootstrap.js:66**

`attachToWindow` suspends at `await win.ZQS_Overlay.init(win, rootURI)` (which itself awaits `Zotero.File.getResourceAsync` for the CSS). `shutdown()` iterates `attachedWindows` — the window is not in it yet, only in `pendingWindows`, which shutdown ignores — and then replaces both Sets. The suspended attach resumes, installs the capture keydown listener, the Notifier observer and the overlay DOM, and calls `attachedWindows.add(win)` on the *new* Set. The plugin is now disabled but fully live. Worse, `startup()` unconditionally does `attachedWindows = new Set()` (bootstrap.js:121) before its attach loop, so a subsequent enable has no record of that window and attaches a SECOND time. `_buildDOM()` removes the previous `#zqs-overlay` element, but the first overlay's bound `keydown` capture listener is a different function object and is never removed — and it calls `event.stopImmediatePropagation()` (src/overlay.js:180), so the live second overlay never sees the hotkey while the stale first one toggles a `_root` that is no longer in the document.

- Failure: User quits Zotero (or disables the plugin from the Add-ons manager) in the few milliseconds while startup's stylesheet read is outstanding. `shutdown()` reports success but the hotkey, the overlay DOM and the item Notifier observer all remain installed on the window — disabling the plugin does not disable it.
