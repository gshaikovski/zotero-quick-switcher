## 1. [CRITICAL] getDisplayTitle() is the only unguarded accessor in getStrings(), so a swallowed loadDataTypes() failure turns into a total search failure
**/Users/george/dev/zotero-search/src/engine.js:169**

search() deliberately swallows a loadDataTypes() rejection (engine.js:321-326, `catch (e) { Zotero.debug(...) }`) and then keeps going into the scoring loop. Every other field read in getStrings() is defended — creators is in a try/catch (149-157), the rest go through safe() (159-166) — but the title is read bare: `title: (item.getDisplayTitle() || '').toLowerCase()`. Zotero.Item.getDisplayTitle() is a thin wrapper over getField('title', false, true), and getField throws Zotero.Exception.UnloadedDataException when the item is identified, the field slot is null and _loaded.itemData is false. The exception propagates out of getStrings -> scoreItem -> the un-wrapped `for (const item of items)` loop in search() and rejects the whole promise.

- Failure: User has a group library that has not finished loading (or a library row that is momentarily missing from Zotero.Libraries._cache — _loadDataTypeInLibrary does `Zotero.Libraries.get(libraryID).name` at dataObjects.js:496 and Libraries.get returns `false`, not undefined, for a miss). - Evidence: /Users/george/.claude/jobs/be8c93f2/tmp/omni/chrome/content/zotero/xpcom/data/item.js:892-896 (getDisplayTitle -> getField('title', false, true)); item.js:291-296 (throws UnloadedDataException when `this._identified && value === null && !this._loaded.itemData`); dataObjects.js:454-468 (dataTypes is the outer loop, so an early failure skips 'itemData' for every library); dataObjects.js:496 (`Zotero.Libraries.get(libraryID).name`) with libraries.js:174-176 (`return this._cache[libraryID] || false`)

## 4. [HIGH] RANK_CAP truncates the candidate list before ranking, and Zotero.Search returns rows in itemID order — so large libraries silently drop the newest matches
**/Users/george/dev/zotero-search/src/engine.js:311**

- Evidence: /Users/george/.claude/jobs/be8c93f2/tmp/omni/chrome/content/zotero/xpcom/data/search.js:639 (`Zotero.DB.columnQueryAsync(this._sql, ...)` with no ORDER BY anywhere in _buildQuery, search.js:959-1833) and search.js:1823-1824 (final SQL is `SELECT itemID FROM items WHERE itemID IN (...) ## 5. [HIGH] tokenize() diverges from Zotero.SearchConditions.parseSearchString on quote characters, collapsing the ranking to 'shortest title first'
**/Users/george/dev/zotero-search/src/engine.js:83**

The comment claims tokenize() 'mirrors Zotero.SearchConditions.parseSearchString closely enough that our ranking agrees with what the DB actually matched'. It does not. parseSearchString splits on `/\s*("[^"]*")\s*|"\s|\s"|^"|"$|'\s|\s'|^'|'$|\s/m`, which explicitly strips UNPAIRED quotes at the start/end of words and strips single quotes too. The plugin's `/"([^"]*)"|(\S+)/g` only handles balanced double quotes; for anything unbalanced the `(\S+)` branch wins and the quote character is retained inside the token. Because the stage-2 fields never contain a `"` or leading/trailing `'`, scoreToken returns 0 on every tier including _subsequenceScore (which bails the moment a token character is absent, engine.js:226). All six perField entries are 0, `best <= 0` fires, and each token contributes a flat 0.01. score becomes 0.01 + the title-length bonus, which is a strictly decreasing function of title length — so the entire result list is ordered by title length ascending, not by relevance.

- Failure: User opens the switcher and starts typing a quoted phrase: `"attention`. tokenize returns ['"attention'] while addCondition's parseSearchString strips the leading quote and the DB correctly searches for 'attention'. Every candidate scores 0.01 + 0.04/(1+log(1+len/60)) — 0.041 for a 20-char title, 0.030 for a 100-char title — so the list is sorted purely by title length and the first result (auto-selected, Enter opens it) is whichever match has the shortest title. Same for a trailing quote (`attention"`), for single-quoted input (`'attention'`), and — because the overlay searches on every keystroke (overlay.js:334-341) — for the entire time the user is mid-way through typing any quoted phrase.
- Evidence: /Users/george/.claude/jobs/be8c93f2/tmp/omni/chrome/content/zotero/xpcom/data/searchConditions.js:785-810 (parseSearchString; the split regex strips `^"`, `"$`, `\s"`, `"\s`, `^'`, `'$`, `\s'`, `'\s`); search.js:307-310 (addCondition routes the quicksearch value through parseSearchString)
- Fix: Derive the ranking tokens from the same function the DB used: `Zotero.SearchConditions.parseSearchString(query).map(p => p.text.toLowerCase())`. That guarantees stage 1 and stage 2 agree by construction and removes the whole class of divergence (quotes, and the NFC normalization addCondition applies at search.js:408, which the plugin also does not replicate).

## 11. [HIGH] Pointer-driven selection silently overrides the keyboard selection (and the "first result preselected" guarantee)
**src/overlay.js:274**

The `mousemove` handler on the result list unconditionally rewrites `_selectedIndex` to whatever row is under the pointer, with no guard that the pointer actually moved. - Evidence: /Users/george/.claude/jobs/be8c93f2/tmp/omni/chrome/content/zotero/elements/tabsMenuPanel.js:78 (Zotero's filterable panel registers only popupshowing/popupshown/popuphiding/keydown; selection is changed only in _handleKeydown:479 and row click handlers - no mousemove-select anywhere)
- Fix: Ignore mousemove unless the pointer really moved: record `event.screenX/screenY` and bail when they are unchanged since the last mousemove; additionally suppress hover-select for one tick after `_render()`/`scrollIntoView()` (a `_suppressHoverUntil` timestamp, or set a flag in `_move()` cleared by the next mousemove with changed coordinates).
